# Local demo data

The application runner calls the transactional `DemoSeedService` after Flyway has created the schema. `foodgo.seed-enabled=true` enables it; the supplied application properties default to `FOODGO_SEED_ENABLED=true`. Set `FOODGO_SEED_ENABLED=false` to disable it. There is no reset, truncate, drop, order-history fabrication, or password update.

New accounts use BCrypt and `foodgo.seed-password` (`FOODGO_SEED_PASSWORD`, default **`FoodGo@123`**). This documented password is for the local demo. Changing the setting only affects accounts that do not exist yet; existing usernames keep their password, role, enabled state, restaurant association, and driver state.

| Username | Role | Fixture |
| --- | --- | --- |
| `customer-1` | CUSTOMER | Minh Anh; address `AREA_A` / `CUSTOMER_A` |
| `customer-2` | CUSTOMER | Khách thứ hai; address `AREA_A` / `CUSTOMER_B` |
| `restaurant-1` | RESTAURANT | Bếp Nhà |
| `driver-1` | DRIVER | Nguyễn An; `AREA_A` |
| `driver-2` | DRIVER | Trần Bình; `AREA_A` |

An existing customer with no address receives one sample address. Customers who already have an address keep their addresses. A reused username with a different role is preserved and receives no customer-only fixtures.

Bếp Nhà is in `AREA_A` at sample point `RESTAURANT_A`. Its six dishes cover the `Cơm` and `Món thêm` categories. The fixture uses the frontend's supported `CHICKEN_RICE` and `MUSHROOM_RICE` image codes; the extra dishes intentionally share those sample illustrations.

Each customer receives a cart only when no cart and no historical order exists for that customer. The two lines are added through `CartService`, so production pricing, option validation, signatures, and cart versions apply:

| Food / option | Price or quantity |
| --- | --- |
| Cơm gà nướng base | 30,000 VND |
| `Kích cỡ` → `Lớn` | +10,000 VND |
| `Món thêm` → `Trứng` | +5,000 VND |
| `Món thêm` → `Rau` | +5,000 VND |
| Configured chicken | 50,000 VND × 2 |
| Cơm nấm kho | 40,000 VND × 1 |
| Cart subtotal | **140,000 VND** |

`Kích cỡ`, `Món thêm`, and `Độ cay` are optional groups. The initial cart selects the three paid options above. A fresh cart has version `2` after the two adds. Always read its current version before a mutation.

Existing carts are left alone, including empty carts after clearing or checkout. Restarting the application does not refill them or increment their version. Existing orders, driver assignments, offers, dishes, prices, availability, and options are not rewritten. If a natural-key fixture already exists with customized catalog values, those values remain authoritative and its cart price can differ from the fresh-install example.

| Offer code | Behavior | Minimum subtotal | Required method |
| --- | --- | --- | --- |
| `TRUA10` | 10% off food, capped at 30,000 VND | 100,000 VND | Any |
| `SHIP5` | 5,000 VND off delivery | 0 VND | Any |
| `FREESHIP` | Free delivery | 100,000 VND | Any |
| `VIFREESHIP` | Free delivery | 100,000 VND | `MOCK_WALLET` |

New offers are valid from 2026-01-01 UTC through 2030-12-31 UTC. Existing offer dates and settings are preserved. With the untouched cart and the standard 15,000 VND delivery fee, the total is 155,000 VND without an offer, 141,000 VND with `TRUA10`, 150,000 VND with `SHIP5`, or 140,000 VND with an applicable free-delivery offer.

## Discovering generated IDs

IDs are generated by MariaDB. Do not assume user, food, option, offer, address, or cart IDs are `1`, `2`, etc. Natural-key lookups make a subsequent startup reuse the rows.

1. Log in with `POST /api/v1/auth/login` using a username and the configured password for a newly seeded account.
2. Use `GET /api/v1/catalog/foods` and `GET /api/v1/catalog/foods/{id}` to locate dishes and their option-group/value IDs by name. Use `GET /api/v1/catalog/offers` for offer codes and IDs, and `GET /api/v1/catalog/restaurants` for the restaurant ID.
3. With the customer token, read `GET /api/v1/addresses` and `GET /api/v1/cart` for address IDs, cart item IDs, selected option IDs, current version, and subtotal. Create orders through quote/checkout and restaurant/driver actions so normal history and state rules apply.

Read-only SQL can also locate the sample rows:

```sql
SELECT id, username, role, restaurant_id, driver_area_code FROM users
WHERE username IN ('customer-1','customer-2','restaurant-1','driver-1','driver-2');
SELECT f.id, f.name, f.base_price, r.name AS restaurant_name
FROM foods f JOIN restaurants r ON r.id=f.restaurant_id
WHERE r.name='Bếp Nhà' ORDER BY f.id;
SELECT f.name AS food_name, g.name AS group_name, v.id, v.name, v.extra_price
FROM option_values v JOIN option_groups g ON g.id=v.group_id
JOIN foods f ON f.id=g.food_id WHERE f.name='Cơm gà nướng' ORDER BY g.sort_order,v.id;
SELECT id, code, required_method FROM offers
WHERE code IN ('TRUA10','SHIP5','FREESHIP','VIFREESHIP');
```

On an otherwise empty database, the seed adds 5 users, 1 restaurant, 2 categories, 6 foods, 3 option groups, 6 option values, 2 addresses, 2 carts, 4 cart items, 6 cart-item option links, and 4 offers. It creates **zero orders**. Existing data can change these counts. On a second startup with no intervening changes, all counts, existing password hashes, cart items, and cart versions remain unchanged.

The runner is intended for a single local application instance. Names and parent associations are the identity of fixtures that lack a database uniqueness constraint; renaming a fixture can cause a new sample row to be added on a later startup. Run one seed-enabled instance when initializing the database.
